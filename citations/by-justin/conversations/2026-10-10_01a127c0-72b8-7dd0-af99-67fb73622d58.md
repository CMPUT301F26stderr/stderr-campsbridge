**For this repository, I’d use [pre-commit](https://pre-commit.com/).** It manages hooks through a checked-in `.pre-commit-config.yaml`, supports multiple languages, and runs checks on staged files.

There isn’t a clear universal adoption winner. Common choices are:

| Tool | Typical fit |
|---|---|
| [pre-commit](https://pre-commit.com/) | Mixed-language repositories; ready-made hook catalog |
| [Husky](https://typicode.github.io/husky/) | JavaScript/TypeScript projects with npm tooling |
| [Lefthook](https://lefthook.dev/) | General projects running existing commands and scripts |

For your Android team, pre-commit’s ready-made checks would keep setup straightforward. Each member installs the tool and runs `pre-commit install` after cloning; the shared configuration stays in Git. [Installation documentation](https://pre-commit.com/#install)

I would start with these checks:

| Check | Purpose |
|---|---|
| Trailing whitespace and final newline | Keep routine formatting consistent |
| YAML, JSON, and TOML validation | Catch malformed configuration |
| Merge-conflict markers | Catch accidentally committed conflicts |
| Large added files | Catch accidental binaries or oversized assets |
| Secret scanning with Gitleaks | Catch accidentally committed credentials |
| Kotlin formatting | Apply one agreed style, using a tool such as ktfmt |

The first four groups are available in the [standard hooks collection](https://github.com/pre-commit/pre-commit-hooks). [Gitleaks](https://github.com/gitleaks/gitleaks#pre-commit) provides a pre-commit integration, and [ktfmt](https://github.com/Kotlin/ktfmt) handles Kotlin formatting.

**Keep commit hooks fast.** I’d leave full Android Lint, builds, device tests, and AI review in GitHub Actions. Unit tests could be an optional `pre-push` hook if they run quickly enough.

Run the hook checks in CI too, using:

```bash
pre-commit run --all-files
```

That provides consistent verification even when someone hasn’t installed local hooks. The framework supports this directly. [CI usage](https://pre-commit.com/#pre-commit-run)

For now, I would skip strict commit-message validation: small PRs, clear descriptions, and consistent squash-merge titles give your team more value with less friction.

**I’d adopt the official Kotlin conventions and enforce formatting with ktfmt’s `--kotlinlang-style`.** That gives your six-person team a shared standard with few formatting decisions to debate. [Kotlin conventions](https://kotlinlang.org/docs/coding-conventions.html), [ktfmt options](https://github.com/Kotlin/ktfmt#using-the-formatter)

Use these rules:

- **Four spaces**, no tabs; let the formatter handle wrapping and spacing.
- **`PascalCase`** for classes and UI composables, such as `Reservation` and `ReservationScreen`.
- **`camelCase`** for ordinary functions and variables, such as `joinWaitlist` and `availableDates`.
- **`UPPER_SNAKE_CASE`** for constants, such as `MAX_GUESTS`.
- Prefer **`val`** and read-only collection interfaces when mutation isn’t needed.
- Use descriptive names and comments that explain decisions or business rules. [Kotlin style guide](https://kotlinlang.org/docs/coding-conventions.html)

Your repository already has `kotlin.code.style=official` in [gradle.properties](https://github.com/CMPUT301F26stderr/stderr-campsbridge/blob/5282afb1424a30bac10ec4d79296ca1037e7a31d/gradle.properties) and four-space indentation in [.editorconfig](https://github.com/CMPUT301F26stderr/stderr-campsbridge/blob/5282afb1424a30bac10ec4d79296ca1037e7a31d/.editorconfig). This recommendation fits those settings.

Make the **same pinned formatter version** authoritative in local hooks and CI. Reviewers can then concentrate on behavior, clarity, and architecture.

If you meant **commit-message style**, I’d use lightweight [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) for PR titles and squash commits:

```text
feat(lottery): allow entrants to leave the waitlist
fix(reservations): prevent overlapping bookings
docs: add onboarding instructions
ci: add Kotlin formatting checks
```

Keep individual working commits flexible initially; enforce the convention on the final merged title.
