**An Android emulator is not inherently required for persistence tests.** My previous recommendation was one testing approach, not a requirement.

The two emulators serve different purposes:

- **Firebase emulator:** provides the local Firestore/Storage backend.
- **Android emulator:** runs an Android operating system.

What the test needs depends on which code it exercises:

| Test | Firebase emulator? | Android device/emulator? |
|---|---|---|
| Date calculations, validation, ID helpers | No | No |
| ViewModel using fake repositories | No | No |
| Actual Firestore/Storage repository | Yes | Android runtime needed; Robolectric may provide it |
| Compose component interactions | Usually no | Can use Robolectric |
| Full app flows and platform integration | When exercising persistence | Device or emulator recommended |

**For persistence tests, Robolectric is the alternative.** It supplies an Android test environment inside the ordinary JVM, without booting a virtual device. Ordinary JVM tests otherwise have Android API stubs whose methods lack implementations. [Android local tests](https://developer.android.com/training/testing/local-tests), [Robolectric](https://robolectric.org/)

That would let us aim for:

```text
JVM test with Robolectric
    → Actual Kotlin repository
    → Android Firebase SDK
    → Transient Firebase emulator
```

These are **integration tests**, even though they run through the local JVM test task. Robolectric provides the Android environment; we still use the real repository and real local Firebase services.

We should first prove this with one Firestore transaction test and one Storage upload/download test against our pinned SDK versions. If compatibility works, the persistence CI job needs no Android virtual device. Firebase itself uses Robolectric for local SDK tests, while also maintaining device-based integration tests. [Firebase Android SDK testing](https://github.com/firebase/firebase-android-sdk#testing)

**For UI tests, we can also use both approaches.** Robolectric supports Compose testing, so buttons, displayed state, validation messages, and many screen interactions can run locally. [Robolectric Compose support](https://robolectric.org/blog/2026/07/03/designing-local-testing-libraries/)

Keep a smaller device/emulator suite for complete app flows and Android-specific behavior: permissions, camera/QR scanning, image picking, navigation, and actual rendering.

For this project, I would therefore start with **plain JVM tests + Robolectric + transient Firebase services**, then add an Android device test job when we have meaningful UI and platform flows to verify.
