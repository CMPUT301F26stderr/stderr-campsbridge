# Global subagent policy

## When to delegate

Use subagents when:

- there's a technically simple yet time consuming task, with a simple goal and not a lot of context to be learnd. Like searching for a functoin, where you don't really care about the process just want the result.
- two or more bounded tasks can proceed independently;
- tests, logs, or documentation would add substantial noise to
  the main thread;
- an independent review would materially improve confidence;

Do not delegate trivial edits, simple questions, or work whose coordination cost
is greater than doing it directly.

Do not delegate tasks that would generate meaningful context, like exploring an unfamiliar codebase, edit large chunks of code, or merge commits. Agents are meant for simple and boring tasks.

## Role selection

- Use `explorer` for read-only codebase mapping and execution-path tracing, only use it when you have something specific in mind (to search something), not to get familiar with codebsae.
- Use `reviewer` after meaningful implementation or configuration changes, only invoke it to review a specific part of the code with specific goal.
- Use `tester` for test execution, reproduction, and failure diagnosis.
- Use `executor` to execute simple commands with potentially a lot of output, like build command for example.

## Coordination

- Give every subagent a bounded task and explicit deliverable.
- Run independent read-only tasks concurrently.
- Avoid concurrent edits to overlapping files.
- Assign clear file ownership before delegating write work.
- Wait for required subagents before producing the final conclusion.
- Request concise summaries rather than raw logs.
- The main agent owns planning, integration, conflict resolution, final
  validation, and communication with the user.
- Treat subagent output as evidence to review, not as automatically correct.
