## Codex — 2026-10-17T03:53:36.822Z

It’s a static website that displays the original Stitch screens and adds navigation from outside them. There’s no build step, framework, or backend.

| File | Purpose |
|---|---|
| [index.html](https://github.com/CMPUT301F26stderr/stderr-campsbridge/blob/5282afb1424a30bac10ec4d79296ca1037e7a31d/prototype/index.html) | The surrounding shell: screen browser, journey selector, toolbar, and phone preview. |
| `screens/*.html` | The 149 original Stitch exports, unchanged on disk. |
| [wiring.json](https://github.com/CMPUT301F26stderr/stderr-campsbridge/blob/5282afb1424a30bac10ec4d79296ca1037e7a31d/prototype/wiring.json) | Screen definitions, connections, branching, and interaction settings. |
| [prototype.js](https://github.com/CMPUT301F26stderr/stderr-campsbridge/blob/5282afb1424a30bac10ec4d79296ca1037e7a31d/prototype/prototype.js) | A generic runner that interprets the JSON and attaches behavior. |
| `prototype.css` | Styles the surrounding shell. |

The phone preview is an iframe, essentially another webpage embedded inside the index page:

```text
index.html
    │
    ├── loads wiring.json
    │
    └── iframe displays screens/<Stitch ID>.html
             │
             └── parent JS listens for interactions
                         │
                         └── looks up the matching JSON rule
                                     │
                                     └── loads the destination screen
```

For example, this is the actual connection for the welcome screen’s Get started button:

```json
{
  "selector": "body > main:nth-of-type(1) > footer:nth-of-type(1) > button:nth-of-type(1)",
  "label": "Get started",
  "action": "goto",
  "target": "01.02"
}
```

The selector identifies the element in the exported HTML. The label makes the rule understandable to someone editing it; it isn’t used to find the button. The target identifies another screen in the JSON.

When you click the button, the parent intercepts that click and changes the iframe’s source to the next HTML file. Because both pages come from the same local server, the parent can access the iframe’s elements.

The same mechanism supports other actions:

- `back`: return to the previous screen.
- `branch`: choose a destination using demo state, such as entrant versus owner.
- `toggle`, `adjust`, and `rating`: handle simple selections.
- `download`: generate a demo CSV.
- `appendMessage`: add a message locally.
- `notice`: explain a control whose device/backend integration is absent.

The JSON also describes conditions. For example, the booking agreement screen identifies its checkbox and Continue button, so the runner disables Continue until the checkbox is checked. Progress screens can have a timed transition to their result screen.

Input values, selections, and messages live in JavaScript memory. The runner restores them when returning to a screen. Restart or reload clears them. Runtime interactions can change the displayed DOM, such as a counter or message bubble, but never rewrite the HTML files.

This remains a navigation prototype. The screens contain their original fixture content; changing a value doesn’t necessarily update another screen’s summary. Maps, calendars, payments, and backend outcomes are simulated or static.

To change a connection, edit `wiring.json`. To introduce a completely new interaction type, add a handler in `prototype.js`. Replacing a design may require updating its selectors because those selectors depend on the HTML structure.

The JSON declares **which choices to remember and where they lead**. JavaScript holds those choices in a small in-memory `state` object.

For your owner example:

1. On the intent screen, this binding maps the two radio buttons to values:

```json
{
  "selector": "input[type=radio]",
  "state": "intent",
  "values": ["entrant", "owner"]
}
```

Selecting the second option makes JavaScript store:

```js
state.intent = "owner";
```

2. After entering your name, Continue uses this rule:

```json
{
  "action": "branch",
  "key": "intent",
  "cases": {
    "owner": "01.05"
  },
  "default": "01.04"
}
```

The runner reads `state.intent`: owners go to **Start Hosting (01.05)**; entrants go to **Interests (01.04)**.

3. On Start Hosting, **Add campsite** has a direct connection:

```json
{
  "action": "goto",
  "target": "10.01",
  "root": true,
  "setRole": "owner"
}
```

That opens campsite setup, changes the preview role to owner, and clears the internal Back trail.

The current navigation state contains only `role`, `intent`, `selectedRole`, and `campsite`. Form values are remembered separately so Back restores your input. **Refresh resets these values; Restart clears them too.**

Standard date/range dialogs can use Material pickers; the availability display needs its own composition. [Date-picker guidance](https://developer.android.com/develop/ui/compose/components/datepickers)

The **image path** should provide photo selection, preview, upload progress, remote display, placeholders, replacement/removal, and recoverable failure. Account and campsite images reuse it. Picking a photo does not itself mean it has been uploaded.

The **map path** should provide stored-coordinate display and location selection for campsite setup. Showing a campsite location should not depend on obtaining the device’s current location. Device-radius discovery remains a later extension.

**6. Shared data access and foreground processing**

Close the known access gaps before feature controllers start compensating for them:

- Published lotteries and campsite-associated lottery lookup.
- Owner-wide reservation observation.
- Reservation/payment refresh or observation.
- Inbox entries assembled with their event content and destination context.

Keep this assembly behind explicit repository contracts or small shared coordinators where combining repositories is necessary. Screens should not implement their own Firestore joins or document-path logic.

Foreground processing needs a usable session-aware contract:

- Resume due lotteries belonging to the relevant owner.
- Resume notification delivery work the acting session can process.
- Retry durable work after relevant operations and foreground return.
- Keep failures in unrelated maintenance work from preventing draws or delivery.
- Stop presentation subscriptions appropriately when their lifecycle ends.

The current global pending-work helper can remain an administrative maintenance entry point. Calling it unchanged from every ordinary account is insufficient.

For the initial dataset, discovery can use bounded published data with application-side filtering. Availability filtering still needs actual calendar data; it cannot infer free dates from the campsite record alone.

**7. Preview, demo, and testing infrastructure**

Build a component gallery and realistic fixture builders before repeating screen implementation.

The gallery should include:

- A short setup step with the keyboard.
- A primary workspace destination.
- A list with loading, empty, and error states.
- A destructive confirmation.
- Calendar modes.
- Missing images, long text, and enlarged text/control sizes.

Provide small controllable fake repositories for controller tests and debug demonstrations. Production wiring must always select real implementations explicitly.

Testing infrastructure should include a controlled clock, coroutine test utilities, repository fakes, and initial Compose interaction-test setup. Existing emulator tests remain responsible for actual queries and transactions.

The foundation is ready when a representative screen can be previewed, tested with a fake, and connected to a real repository without changing its content composable.

**For feature implementation, I would use the following sequence.**

**A. Accounts and onboarding establish a real session.**

Implement Welcome, intent selection, name setup, the owner/entrant branch, profile details, contact editing, profile images, and policy readers.

Account creation and owner activation must survive retries without replacing existing records. Completing setup enters the correct workspace; returning restores the existing profile.

Verify initialization failures, interrupted setup, profile-save failures, optional contact fields, and photo failures.

**B. Campsite management creates the shared inventory.**

Implement the owner list, setup wizard, detail sections, location/photo entry, offered-night editing, and publication.

Use one draft across setup steps. Save a draft identity once and reuse it as later steps succeed. Treat image upload, campsite fields, and offered-night saves as operations with their own confirmed state.

Handle partial calendar saves by refreshing persisted values and retaining unsaved selections.

The completion condition is that a published campsite and its offered nights can be read from another account.

**C. Discovery makes those campsites usable by entrants.**

Implement search, filters, results, campsite details, map display, and calendar inspection.

Define and test search matching, location matching, guest limits, date-range availability, and stable ordering. Preserve applied filters when returning from details. Distinguish no matches from unavailable data.

Connect campsite details to its relevant lotteries. A single eligible lottery can open directly; multiple candidates need selection.

**D. Lottery setup and participation complete the entry flow.**

Implement the single-campsite lottery wizard:

```text
Basics → offered nights → registration window
→ booking window → maximum winners → review → publish
```

Then implement owner management/participants and entrant join/leave states.

Reuse the domain window checks. Derive display states from saved facts and the injected clock; do not persist another lifecycle enum.

Connect automatic foreground drawing and manual fallback to the same draw operation. Present drawing progress and expose final outcomes only after draw completion.

Verify timing boundaries, empty draws, repeated execution, withdrawn entrants, and participant-list updates.

**E. Booking turns a winning opportunity into a reservation.**

Implement date selection, guest input, rules acknowledgement, review, confirmation progress, and the saved reservation overview.

Combine the winning opportunity, booking window, offered nights, current availability, price, and rules into the displayed state. A selected range does not hold inventory.

Confirmation calls the existing coordinated booking operation once. Recover explicitly from unavailable dates, changed prices/rules, expiry, and uncertain acknowledgement. Navigate to the saved reservation only after confirmed success.

Verify that conflicting attempts create no partial reservation or simulated charge.

**F. Reservation management completes the cancellation loop.**

Implement entrant and owner active lists, the shared detail screen, accepted terms, payment/refund display, cancellation, and owner rejection.

Use one reservation-classification function based on saved cancellation and campsite-local dates. Update on foreground return and relevant date boundaries.

Add the accepted checkout cutoff to the public cancellation operation, preserving idempotent retries and the separate moderation-cleanup behavior.

Verify that cancellation/rejection removes the stay from Active, records a full simulated refund, releases nights, and retains historical booking facts.

**G. Inbox and alerts complete result delivery.**

Build the shared Inbox presentation alongside lottery drawing, then finish its feature behavior:

- Win/loss content and correct destinations.
- Stable ordering and first-read acknowledgement.
- Alert preference persistence.
- OS permission handling and permitted alerts.
- Duplicate-alert prevention.
- Recovery when a destination is unavailable.

Keep event persistence, Inbox receipt creation, and OS alerts as distinct states. Disabling alerts retains Inbox history.

**H. Administration reuses the completed presentation paths.**

Implement read-only browsing and inspection for campsites, profiles, images, and notification logs.

Reuse existing detail components where appropriate, while keeping participant actions out of administrative inspection. Handle unavailable parent records and missing image objects explicitly.

Destructive moderation and message logs remain outside this implementation slice.

For every feature, the implementation sequence should be consistent: define its state and pure rules, add focused tests, build previewable content, wire the controller/repositories, then verify real interactions. This keeps the shared foundation useful without requiring a large abstraction framework upfront.
