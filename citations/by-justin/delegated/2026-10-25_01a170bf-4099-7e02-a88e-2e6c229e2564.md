## Stale or potentially misleading design notes

- [DESIGNS.md:85–87](doc/screens/DESIGNS.md) says the calendar implementation choice “remains pending a small working prototype.” A Compose `CampsiteCalendar` with month navigation, status legend, selection semantics, previews, and UI tests already exists. The actual **prototype/layout choice is no longer pending**; the calendar’s feature-specific inventory and persistence behavior still belongs to its callers.
- [DESIGNS.md:113](doc/screens/DESIGNS.md) asks for a “calendar prototype” as part of a future component gallery. Existing calendar previews and UI tests cover a basic visual/interaction prototype. A centralized gallery itself is not evident, so the plan should not imply all calendar work is complete or require a new gallery solely to repeat those previews.
- [doc/screens/stitch/CONSISTENCY.md:9,31](doc/screens/stitch/CONSISTENCY.md) repeats that a shared availability component must be prototyped and that calendar library/layout selection is runtime work. The calendar layout is already implemented with Compose layouts; selection-specific allocation, eligibility, and partial-save behavior remains feature work.
- [DESIGNS.md:50](doc/screens/DESIGNS.md) explicitly says its inventory describes responsibilities rather than existing APIs. That is accurate, but for implementation planning it should be supplemented with the concrete API inventory above so the team does not rebuild controls that already exist.

Recommended planning rule: first compose these controls into feature screens. Add or change a shared component only when the current API cannot express a requirement or when a repeated visual/interaction rule needs a real shared owner. Do not treat the generic calendar as implementing date eligibility or save/retry rules.
