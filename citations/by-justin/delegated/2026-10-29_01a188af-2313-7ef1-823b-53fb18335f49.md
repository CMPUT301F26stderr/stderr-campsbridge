## Codex — 2026-10-29T17:58:36.961Z

I compared current `HEAD` with `origin/main`. The repository already has the booking persistence contract. The new compile-time coupling is in navigation, factories, and test setup.

`ReservationContext` is currently declared inside `ReservationDetailUiState.kt:6`, which is absent from `main`. Both `BookingNavigation.kt` and `InboxNavigation.kt` import it. `AppDestination.kt` also adds the shared booking, reservation, and Inbox route helpers. A booking or Inbox branch based on `main` therefore needs those small shared contracts before it can compile.

The feature graphs otherwise depend on their own screens and ViewModels:

- `bookingGraph(controller, factory)` uses booking types and the shared reservation destination for its success path ([BookingNavigation.kt:22](https://github.com/CMPUT301F26stderr/stderr-campsbridge/blob/5282afb1424a30bac10ec4d79296ca1037e7a31d/app/src/main/java/io/github/CMPUT301F26stderr/campsbridge/navigation/BookingNavigation.kt)).
- `reservationGraph` and `reservationListGraph` both use reservation screens and ViewModels ([ReservationNavigation.kt:30](https://github.com/CMPUT301F26stderr/stderr-campsbridge/blob/5282afb1424a30bac10ec4d79296ca1037e7a31d/app/src/main/java/io/github/CMPUT301F26stderr/campsbridge/navigation/ReservationNavigation.kt), [ReservationNavigation.kt:87](https://github.com/CMPUT301F26stderr/stderr-campsbridge/blob/5282afb1424a30bac10ec4d79296ca1037e7a31d/app/src/main/java/io/github/CMPUT301F26stderr/campsbridge/navigation/ReservationNavigation.kt)). Keep these in one reservation task, or split the file before assigning the work.
- `inboxGraph` only needs the shared reservation route when opening a notification; it does not import the reservation graph itself ([InboxNavigation.kt:75](https://github.com/CMPUT301F26stderr/stderr-campsbridge/blob/5282afb1424a30bac10ec4d79296ca1037e7a31d/app/src/main/java/io/github/CMPUT301F26stderr/campsbridge/navigation/InboxNavigation.kt)). It still needs the reservation graph registered at runtime for that link to open.

The larger conflict is central wiring. `AppNavigation` takes every new feature factory as a required parameter and registers all graphs directly ([AppNavigation.kt:61](https://github.com/CMPUT301F26stderr/stderr-campsbridge/blob/5282afb1424a30bac10ec4d79296ca1037e7a31d/app/src/main/java/io/github/CMPUT301F26stderr/campsbridge/navigation/AppNavigation.kt), [AppNavigation.kt:203](https://github.com/CMPUT301F26stderr/stderr-campsbridge/blob/5282afb1424a30bac10ec4d79296ca1037e7a31d/app/src/main/java/io/github/CMPUT301F26stderr/campsbridge/navigation/AppNavigation.kt)). `AppRoot` mirrors those factory parameters and calls every callback whenever the session is ready ([AppRoot.kt:47](https://github.com/CMPUT301F26stderr/stderr-campsbridge/blob/5282afb1424a30bac10ec4d79296ca1037e7a31d/app/src/main/java/io/github/CMPUT301F26stderr/campsbridge/ui/app/AppRoot.kt), [AppRoot.kt:118](https://github.com/CMPUT301F26stderr/stderr-campsbridge/blob/5282afb1424a30bac10ec4d79296ca1037e7a31d/app/src/main/java/io/github/CMPUT301F26stderr/campsbridge/ui/app/AppRoot.kt)). That eagerly creates factory objects; the actual ViewModels remain route-scoped. `MainActivity` supplies the closures, while `ViewModelFactories.kt` imports and constructs all the new feature ViewModels. `TestAppHost` has a similar all-feature dependency for instrumented tests.

For five independent, buildable branches, I recommend a lead-owned base commit that:

1. Moves `ReservationContext` into its own shared file and establishes the booking, reservation, and Inbox route names in `AppDestination`.
2. Adds stable graph entrypoints for booking, reservation detail/list, and Inbox. Until implemented, each shows explicit pending content.
3. Wires those entrypoints into `AppNavigation` once, with feature construction behind each graph. The graphs can use `AppServices` or a small shared repository-and-clock bundle; feature-owned factory files then import only their own ViewModels.
4. Keeps `TestAppHost` focused on supplying fakes, rather than importing every feature ViewModel.

Each branch can then replace its own pending graph and add its feature files without editing `AppNavigation`, `AppRoot`, `MainActivity`, or the shared test host. The reservation graph can remain one branch so its detail/list screens and shared navigation file stay together. No plugin registry or extra Gradle module is needed.

This base takes more work than one final lead-owned wiring commit. The tradeoff is that the five branches can compile and merge independently from the same base, and the root app can navigate to a clear pending screen while a feature is still unimplemented. A single final integration commit is smaller, but the feature branches would not be individually reachable from the app until that commit lands.
