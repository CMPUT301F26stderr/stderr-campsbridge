# Offline debug demo

Select the `debug` variant in Android Studio and run `app`. The launcher opens an existing entrant in Explore; Profile is available as a tab. It uses the real root, profile, image and navigation code with local repository implementations. Firebase auto-initialization is removed from the debug manifest; the host never accesses Firebase application services.

**Demo tools** offers existing entrant, existing owner, new account, reset scenario, onboarding previews and the component gallery. Reset recreates the selected scenario. Scenario switching clears its ViewModel store and subscriptions before showing the next graph. Activity recreation retains the graph; finishing the host or restarting the process discards its in-memory state. Photo bytes are private cache files and can be evicted by Android; they are never uploaded.

Implemented local interactions include profile observation, capability-limited workspace switching, native photo selection, explicit photo save/replacement/removal, and account/preference operations used by onboarding. The new-account scenario stops at the reserved display-name validator. The preview chooser displays later steps without saving or advancing; Back returns to the demo host. Owner campsite reads/setup and the Explore/filter/detail routes use the shared production content. Saved detail and owner preview include About, Map, read-only Availability and Rules/policy readers. The H03 task example separately supports local availability changes after its helper is connected. Campsite writes, bookings, lottery coordination and push delivery are not simulated. Explore matching awaits the reserved predicates, and the demo review source supplies an explicitly empty read-only dataset.

`AppRepositories` is the feature dependency boundary. `DemoAccountRepository`, `DemoAppPreferences`, `DemoImageRepository`, `DemoCampsiteRepository` and `DemoReviewRepository` provide local behavior without unit-test failure hooks. Add demo behavior alongside the first real consumer. Keep shared business rules in their existing owner and never implement reserved teammate functions as a demo fallback.

Select `firebaseDebug` to run the real Firebase-backed app, or build `release` for delivery. These variants use `MainActivity` and exclude the demo launcher, menu and local repositories. The existing `firebaseEmulatorHost` Gradle property selects emulator endpoints only for Firebase-enabled hosts; see the [Firebase guide](../../../../../../../../../firebase/README.md).

Run controller/data contracts with `:app:testDebugUnitTest --tests '*demo.*'`. Device tests in `demo/OfflineDemoTest.kt` launch the package's default launcher, verify real content and scenario controls, and assert that no Firebase app has been initialized.

The debug Task examples catalogue supplies H01/H02 profile exercises, H03 availability, and H04 owner inventory against local repositories. H03 starts in May 2027 with a booked May 13; H04 retains the supplied fixture order until its helper is connected. H05/H06 isolate discovery text and guest-capacity matching. Bindings remain null in the shared baseline and are supplied independently in each task handoff. Later examples are explicit placeholders.

H05/H06 are available directly in Task examples. Each uses the real Explore controller, working filter child and supplied listings; only its assigned predicate is left pending. Other predicates and ordering use fixed fixture outcomes within that isolated example. The ordinary app retains its pending production helper bindings.
